# SDLC CLI engine setup

The SDLC pipeline's coding-agent phases (classify/plan/implement) run as a
real CLI subprocess (`agents/sdlc_cli_engine.py`) inside its own container,
`sdlc-worker`. It is optional and off by default. Enable it with:

```bash
./sdlc-setup.sh
```

`./install.sh` offers to run this for you interactively at the end of a
fresh install. It is also a standalone, re-runnable script — say no during
install and run it later at any time, or re-run it whenever you change your
LLM provider in `.env`.

## What it does

1. **Fetches the `ainxt` CLI binary from GitHub Releases**
   (`npci/ainxt-cli`) — for the architecture the
   `ainxt-enterprise:local` **container** runs, not this host's OS/arch. The
   binary only ever executes inside the Linux `sdlc-worker` container
   (`docker-compose.yml` bind-mounts it to `/usr/local/bin/ainxt`), so a
   binary built for your Mac or Windows host would silently fail to run
   there. The download is checksum-verified (`.sha256` asset) before it's
   made executable. Never committed to the repo — see `.gitignore`.

   If the release repo is private, `sdlc-setup.sh` tries an unauthenticated
   fetch first, then prompts for a GitHub token and saves it to `.env` as
   `SDLC_CLI_GH_TOKEN` so future runs don't ask again.

2. **Renders `bin/config.toml`** from whichever LLM provider key is
   currently in `.env` — the same priority `choose_provider()` uses:
   `ANTHROPIC_API_KEY` > `OPENAI_API_KEY` > `GEMINI_API_KEY` > Ollama. This
   file is regenerated fresh **every run**, so hand edits to it don't
   survive — change the provider/key in `.env` and re-run this script
   instead.

   If no provider is configured at all, `bin/config.toml` is left absent
   and SDLC stays disabled. You have two options:
   - Add a provider key to `.env` and re-run `./sdlc-setup.sh`, or
   - Copy `bin/config.toml.example` to `bin/config.toml` yourself and fill
     in a custom endpoint (a self-hosted gateway, a provider this script
     doesn't cover, capability overrides, etc.). Once `bin/config.toml`
     exists without the `# GENERATED by sdlc-setup.sh` marker on its first
     line, this script treats it as hand-written and never touches it
     again.

3. **Starts `sdlc-worker`** once both `bin/ainxt` and `bin/config.toml`
   exist.

## Changing your provider later

Update the key in `.env`, then re-run `./sdlc-setup.sh` — it re-renders
`bin/config.toml` for the new provider and restarts `sdlc-worker` with it.

## Troubleshooting

- `docker compose logs sdlc-worker` — the worker's own startup/runtime logs.
- `rm bin/ainxt && ./sdlc-setup.sh` — force a re-fetch of the CLI binary.
- If the CLI needs a provider this script doesn't model exactly right (the
  Gemini block is marked unverified in `bin/config.toml.example` for a
  reason), hand-write `bin/config.toml` — see its own header comment and
  the CLI's bundled `~/.ainxt/docs/user-guide/11-custom-models.md` for the
  full schema.
